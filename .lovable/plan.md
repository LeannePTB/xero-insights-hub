## 1. The access matrix — one source of truth

Two files, generated-from-one:

- `docs/security/access-matrix.ts` — the authoritative data. An exported array of rows: `{ role, resource, operation, expect: "allow" | "deny", rule, knownFailure?: { backlog: number, note: string } }`. `rule` cites Project Knowledge rule number or Access Control Spec section.
- `docs/security/access-matrix.md` — a readable table for the owner, **generated** from the `.ts` by `bun run scripts/render-access-matrix.ts`. A vitest case fails if the `.md` is stale, so the document and the tests can never disagree.

Roles: org owner; org staff; member of a different organisation; client viewer; support-grant holder (read-only, non-member org); super admin with no membership; suspended member; removed member; member holding aal1 only; anonymous.

Resources: `firms`, `firm_members`, `clients`, each client-data table (`client_xero_orgs`, `client_notes`, `client_access`, `client_cost_classifications`, `client_true_breakeven_inputs`, `client_reports`, `client_subscriptions`, `unreconciled_lines`, `unreconciled_uploads`, `reconciliation_snapshots`, `loan_consolidation_*`, `tier_widget_config`, `report_cache`, `audit_findings`), `xero_connections` non-token columns, `xero_connections.access_token_enc`/`refresh_token_enc`, `xero_snapshots`, `audit_log`, `subscriptions`/billing, Path C metadata (`admin_firm_overview`, `plan_levels`, `tier_settings`, `signup_requests`, `invites`, `user_roles`, `xero_api_errors`), `user_presence`, `profiles` (own vs other row; `display_name` vs `email` column), every SECURITY DEFINER function EXECUTE-able by `authenticated`, and the named server functions (list clients, read Xero data, write client data, invite, support request/approve, ownership transfer).

Operations: read / insert / update / delete, plus execute for functions.

## 2. Database access tests — recommendation

**Recommend (b), by extending the harness that already works**, not (a).

- (b) is already proven in this repo: PGlite accepts `set local role authenticated` with injected `request.jwt.claims`, and everything rolls back. Runs in seconds, touches no real organisation, client, Xero or profile data, makes no Xero call, and needs no production auth accounts. `aal` is just another claim, so aal1 vs aal2 is testable directly. `SET ROLE` inside SECURITY DEFINER is irrelevant here — the role is set by the harness before the call, not inside the function.
- (a) is rejected for this phase: it creates real production auth accounts with real TOTP secrets, needs exclusion plumbing in the posture card's people counts and online list, and adds test rows to the real database. Cost and blast radius are wrong for a guardrail that must run after every change.
- (c) a separate database or branch is not available on this platform in a form I can verify, so it is not proposed.

The one real weakness of (b) is drift: the fixture is a mirror, so a live change that is not re-dumped is invisible. Mitigations, both included in this phase:

1. `scripts/dump-rls-fixture.sh` is extended to dump **all** policies (not just SELECT-capable), table grants and column grants, definer function bodies for the callable set, and a trailing `-- catalogue-fingerprint: <sha256>` line.
2. A new read-only server check recomputes the live fingerprint and compares it to the fixture's. Mismatch = the matrix tests are stale, surfaced as Warn on the posture card and printed by the test command.

Optionally, later phases can add (a) as a small smoke test against one throwaway organisation. Not in Phase 2.

## 3. Known defects stay visible

Matrix rows carrying `knownFailure` are asserted **inverted**: the test asserts current (wrong) behaviour and fails loudly if it changes. Every run prints a `KNOWN FAILURE` block listing rule, resource, operation and backlog number; the count is reported separately and never folded into passes. Removing the marker (a later phase's fix) makes the test assert the matrix expectation instead. Seeded from backlog item 18 (support-grant writes through `user_can_manage_client`) and item 19's related pending decision.

## 4. Static guard tests (`tests/static-guards.test.ts`, existing vitest run)

Source-scanning tests over `src/`:

1. Every `createServerFn` chain uses `requireAal2`, unless its exported name is in `docs/security/server-fn-aal1-allowlist.ts` with a reason. Covers the two aal1 loggers (`logAuthEvent`, `logLogin`) and the unauthenticated functions. Unlisted new function = failing test.
2. Every `supabaseAdmin` usage site (file + enclosing function) appears in `docs/security/admin-client-register.md`, each marked `system context` or `exception — calls DB authorisation first`. The register is created in this phase from today's 58 real usage files. Unregistered new use = failing test.
3. No `profiles` query selecting or filtering on `email` for identity/recipient decisions (allow-list for display-only sites, each with a comment).
4. No `tenantId`/`tenant_id` read from a request body, query string or header in server code.

## 5. Wiring the proof in

- `definer_guards` in `public.security_posture()` tightened: a callable definer function must call `app_private.assert_aal2()` or `app_private.is_aal2()` specifically; the documented exclusion list is `public.xero_required_scopes` (plus anything the owner approves). Any other unmatched function = Action.
- New `access_tests` check in the same function, reading a new table `public.security_test_runs` (`id, ran_at, ran_by, passed, failed, known_failures jsonb, fingerprint_match bool`): Action if the last run had unexpected failures; Warn if never run or older than 7 days; OK otherwise. Known failures listed with backlog numbers in the details.
- `/admin/security` gets a super-admin-only **Run access tests** button, calling an aal2 server function whose authorisation is the database function `public.record_access_test_run(...)` (asserts aal2 + `app_private.me_is_super_admin()` first). Results shown per role, with last-run time and who ran it. Runs are recorded in `security_test_runs`, **not** `audit_log` — a test run is not an access or security event.
- Single command the agent must run after every security-relevant change: **`bun run security:check`** = re-dump the fixture, run the matrix + static guard suites, compare fingerprints, record the run. **Pass** = zero unexpected failures, fingerprint matches, and the known-failure set is unchanged from the recorded baseline.

## Effort and how Phase 2 is proved to work

Roughly a day's work in one pass: matrix and generator, fixture dump extension, two test suites, register and allow-list, migration, button and posture wiring.

Self-proof, entirely inside the PGlite fixture and reverted in the same test run: a `meta` test loads the fixture, drops one policy (e.g. the organisation filter on `clients`) inside a transaction, re-runs a matrix case, asserts the suite reports a failure, then rolls back. Nothing touches the live database, no real data is read or written, and no Xero call is made. A second meta case appends a fake `createServerFn` without `requireAal2` to an in-memory source string and asserts the static guard flags it.
